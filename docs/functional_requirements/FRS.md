# Спецификация функциональных требований (Functional Requirements Specification — FRS)
## Проект: AccessFlow — Employee Access Management

| Версия | Дата | Автор | Статус |
|---|---|---|---|
| 1.0.0 | Октябрь 2026 | Ведущий системный аналитик | Утверждено |

---

### 1. Архитектурный обзор и роли пользователей

Система AccessFlow реализует ролевую модель доступа (RBAC) со следующими ролями пользователей:
1. **EMPLOYEE (Сотрудник)**: может просматривать каталог систем, создавать заявки от своего имени, отслеживать их статус, отменять поданные заявки до завершения согласования.
2. **MANAGER (Руководитель)**: согласует или отклоняет заявки сотрудников своего департамента.
3. **SYSTEM_OWNER (Владелец системы)**: согласует предоставление привилегированного доступа к закрепленной за ним информационной системе.
4. **SECURITY_OFFICER (Офицер ИБ)**: согласует все заявки, содержащие признак привилегированного доступа (`is_privileged = true`), после согласования руководителем и владельцем.
5. **ADMIN (Администратор системы)**: управление справочниками систем, ролей, ручной перезапуск упавших задач провижининга, аудит.

### 2. Функциональные требования (FR)

#### Модуль 1. Управление заявками (Request Lifecycle)
- **FR-01: Создание заявки на доступ**
  - Пользователь с ролью `EMPLOYEE` может создать заявку, указав идентификатор целевой роли (`role_id`), срок действия доступа (`valid_to` - опционально, по умолчанию постоянный) и бизнес-обоснование (`justification`, мин.длина 10 символов).
  - Система проверяет актуальность сотрудника в HRIS (статус `ACTIVE`). При неактивном статусе возвращается ошибка `403 Forbidden` с описанием.
  - При наличии у сотрудника уже действующего доступа с этой же ролью или находящейся на согласовании заявки система отклоняет создание заявки с кодом `409 Conflict`.
- **FR-02: Автоматическое определение маршрута**
  - Система определяет признак привилегированности запрашиваемой роли:
    - Если `is_privileged == false`: статус заявки выставляется в `PENDING_MANAGER`.
    - Если `is_privileged == true`: статус заявки выставляется в `PENDING_MANAGER`, формируется план согласования из 3 этапов (`MANAGER` -> `SYSTEM_OWNER` -> `SECURITY_OFFICER`).
- **FR-03: Просмотр реестра заявок**
  - Сотрудник видит только свои заявки.
  - Согласующий видит заявки, ожидающие его резолюции, а также архив согласованных им заявок.
  - Администратор и ИБ имеют право сквозного просмотра всех заявок.
  - Реализована пагинация (`limit`, `offset`), фильтрация по `status`, `system_id`, `created_at`.
- **FR-04: Отмена заявки сотрудником**
  - Сотрудник может отменить заявку в статусах: `DRAFT`, `PENDING_MANAGER`, `PENDING_OWNER`, `PENDING_SECURITY`.
  - Заявка переходит в статус `CANCELLED`.
  - Отмена невозможна, если заявка уже находится в статусах `APPROVED`, `IN_PROVISIONING`, `PROVISIONED`, `REJECTED`, `CANCELLED`.

#### Модуль 2. Согласование и резолюции (Approval Workflow)
- **FR-05: Вынесение резолюции согласующим**
  - Согласующий отправляет запрос с решением: `APPROVED` или `REJECTED`.
  - При отклонении (`REJECTED`) обязательным является указание причины (`comment`, мин.длина 5 символов).
  - При принятии решения проверяются права пользователя:
    - На этапе `PENDING_MANAGER`: согласующий должен являться непосредственным руководителем сотрудника (согласно данным HRIS).
    - На этапе `PENDING_OWNER`: согласующий должен быть назначен владельцем целевой информационной системы.
    - На этапе `PENDING_SECURITY`: пользователь должен обладать ролью `SECURITY_OFFICER`.
- **FR-06: Продвижение по цепочке согласования**
  - Если на этапе `PENDING_MANAGER` вынесено `APPROVED`:
    - Для стандартной роли: заявка переходит в статус `APPROVED`.
    - Для привилегированной роли: заявка переходит в статус `PENDING_OWNER`.
  - Если на этапе `PENDING_OWNER` вынесено `APPROVED`:
    - Заявка переходит в статус `PENDING_SECURITY`.
  - Если на этапе `PENDING_SECURITY` вынесено `APPROVED`:
    - Заявка переходит в статус `APPROVED`.
  - При вынесении `REJECTED` на любом этапе:
    - Заявка немедленно переходит в статус `REJECTED`, оставшиеся этапы аннулируются.

#### Модуль 3. Исполнение и интеграция с IAM (Provisioning)
- **FR-07: Инициирование провижининга**
  - При переходе заявки в статус `APPROVED` система автоматически переводит её в статус `IN_PROVISIONING` и инициирует асинхронный вызов IAM API.
  - В запрос к IAM передаются: `idempotency_key` (UUID заявки), `employee_id`, `system_code`, `role_code`.
- **FR-08: Обработка результатов провижининга**
  - При получении HTTP `200 OK` или `201 Created` от IAM: статус заявки изменяется на `PROVISIONED`, фиксируется дата выдачи.
  - При HTTP `5xx` или сетевом таймауте:
    - Система инициирует до 3 повторных попыток (Exponential Backoff: 1s, 2s, 4s).
    - Если все попытки исчерпаны: статус переходит в `FAILED`, создается запись об инциденте для администратора.
  - При HTTP `4xx` (бизнес-ошибка IAM, например, конфликт учетных записей): заявка переходит в статус `FAILED` с сохранением кода и текста ошибки из IAM.
- **FR-09: Ручной перезапуск провижининга**
  - Пользователь с ролью `ADMIN` может вызвать повторный провижининг для заявки в статусе `FAILED`.

#### Модуль 4. Журнал аудита (Audit Trail)
- **FR-10: Протоколирование операций**
  - Каждая модификация состояния заявки (создание, смена статуса, резолюция, ошибка IAM) атомарно записывается в таблицу `audit_logs`.
  - Атрибуты записи: `event_id`, `timestamp`, `entity_name`, `entity_id`, `action`, `actor_user_id`, `old_values` (JSON), `new_values` (JSON), `ip_address`, `comment`.
  - Записи журнала аудита доступны только для чтения (WORM — Write Once, Read Many).

### 3. Бизнес-правила (Business Rules)

| Код | Название правила | Логика валидации |
|---|---|---|
| **BRule-01** | Активность сотрудника | Заявка может быть создана только если `HRIS.get_employee(emp_id).status == 'ACTIVE'`. |
| **BRule-02** | Запрет самосогласования | Руководитель не имеет права согласовывать заявку, созданную им самим для себя (Segregation of Duties). |
| **BRule-03** | Уникальность активного доступа | Нельзя подать заявку на роль `R`, если у сотрудника уже есть действующая роль `R` в системе `S` или открытая заявка со статусом `!= REJECTED, CANCELLED`. |
| **BRule-04** | Обязательность обоснования отказа | Резолюция `REJECTED` без заполненного поля `comment` запрещена (длина ≥ 5 символов). |
| **BRule-05** | Идемпотентность интеграции | Повторная отправка запроса в IAM с тем же `idempotency_key` не должна приводить к дублированию назначений или ошибке. |
| **BRule-06** | Границы отмены | Отмена заявки доступна только до перехода в финальное согласование (`APPROVED`). |

### 4. Нефункциональные требования (NFR)

#### 4.1. Производительность (Performance & Scalability)
- **NFR-01**: Время отклика API на операции чтения (каталог, просмотр заявки) ≤ 200 мс (95-й перцентиль) при нагрузке 100 RPS.
- **NFR-02**: Время отклика API на операцию создания заявки (включая синхронную валидацию в HRIS) ≤ 500 мс.
- **NFR-03**: Пропускная способность модуля провижининга: обработка не менее 50 заявок в секунду в пиковые часы.

#### 4.2. Надежность и доступность (Reliability & Availability)
- **NFR-04**: Коэффициент доступности системы (Availability SLA) — не менее 99.9% в режиме 24/7/365.
- **NFR-05**: RPO (Recovery Point Objective) ≤ 1 минута; RTO (Recovery Time Objective) ≤ 15 минут.
- **NFR-06**: При сбое внешних сервисов (HRIS/IAM) система должна применять шаблон **Circuit Breaker** и **Retry with Exponential Backoff**, предотвращая каскадные отказы.

#### 4.3. Безопасность (Security)
- **NFR-07**: Аутентификация запросов через JWT (Bearer token).
- **NFR-08**: Контроль доступа на уровне сущностей и методов API (RBAC + ABAC по принадлежности к подразделению).
- **NFR-09**: Защита от OWASP Top-10: экранирование SQL-инъекций (SQLAlchemy ORM), валидация входных данных через строгие схемы Pydantic, санитизация XML против XXE-атак.
- **NFR-10**: Все сетевые коммуникации осуществляются по протоколу TLS 1.3.

#### 4.4. Сопровождаемость (Maintainability)
- **NFR-11**: Документирование REST API в стандарте OpenAPI 3.1 с автогенерацией Swagger UI.
- **NFR-12**: Покрытие бизнес-логики модульными и интеграционными автотестами не менее 85%.
- **NFR-13**: Контейнеризация всех компонентов через Docker и Docker Compose.
